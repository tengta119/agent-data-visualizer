## ⚠️ 面试 / 演示前必须处理

当前工作区代码与本文描述的审批设计**不一致**，是调试中间态（与 `QA-D1-D5` 第一节所述为同一处）：

- `ShellExecutor` 中 `review.isForbidden()` 快速拒绝、以及"批准后二次审查"被注释，且 `if (true)` 强制**所有**命令走审批；
- `CommandPolicyReviewer` 末尾 `promptMatched = true;` 无条件覆盖，导致 `ALLOW` 分支不可达（命中允许规则的命令也会变成待审批）。

本文 D0 的口径是"默认拒绝 + 允许规则直接执行 + 批准后二次审查"。**若带着当前代码去演示，讲的和跑的对不上**，面试官现场读代码会发现。演示前请先恢复这两处。

## D0. 请介绍一下你这个项目

**Q：先简单介绍一下你最近做的这个项目。**

### A：面试回答（90 秒主力版）

我这个项目是一个 **AI 驱动的「数据搜集 + 自动绘图」工作台**。用户在网页上用自然语言描述需求，后端会拉起一个 Agent 工作流，依次做需求分析、生成图形结构、最后自审一遍，最终产出一张能在页面上直接看的架构图或者时序图。绘图这部分之所以要"搜集数据"，是因为 Agent 中间会去调本地或者远程机器的命令，把真实的环境信息拿到手，再画进图里。

技术形态上，后端是一个 **模块化单体的 Spring Boot 服务**，前端是独立的 Next.js 应用，中间走 HTTP。这里我没有做微服务拆分，因为整套业务链路本质上是"一次请求跑完一个 Agent 工作流"，拆开只会把会话、流式推送和配置状态的一致性成本抬上去，收益不成立。

Agent 这块我用的是 Google 的 ADK，它本质上是一套 **Agent 执行框架**，允许你注册回调，在模型调用、工具调用这些阶段插入自己的逻辑。我是完全 **配置驱动** 的：Agent 的模型端点、子 Agent、工作流顺序都写在 YAML 里，启动的时候由装配链把配置翻译成可运行的执行器，并且按 Agent ID 注册成 Spring 里的 Bean。默认那条链路是"分析 → 绘图 → 审查"三个子 Agent 串行跑。

我个人觉得这个项目最有价值的三块，都不是业务代码，而是 **把一个"大模型应用"做成"可控服务"** 的那部分：

第一块是 **绘图的稳定性**。最初我是让模型直接输出 Draw.io 的 XML，结果非常不稳，结构经常不合法、坐标乱飞，前端渲染不出来。后来我改成让模型只输出一份 **紧凑的 JSON 中间表示**——只描述节点、连线和语义类型，不带坐标也不带样式，XML 由服务端确定性地生成。这样模型只负责它擅长的事，格式正确性由后端保证。

第二块是 **Agent 工具的安全边界**。Agent 能执行本机 shell 命令，这是很大的风险面。所以我加了一层 **命令策略审查**，分成允许、需要审批、直接拒绝三态，默认是不允许的；需要审批的命令会通过流式连接推给用户，用户点"允许一次"才执行，而且批准之后还要再校验一次命令内容。另外本地 shell 我是 **按请求隔离** 的：每个对话请求持有自己独立的进程，同一请求内多条命令复用、请求结束就销毁；真正写 shell 的动作走一个有界单线程执行器，保证同一时刻只有一个线程写它，并且带超时，**超时只销毁触发超时的那一个请求的 shell**，不会影响别人。

第三块是 **执行过程的可观测**。流式接口会把 Agent 运行、模型调用、工具调用都实时推给前端。这里有个容易踩的坑：日志处理器如果全局共享，多个人同时用就会串线，所以我是每个请求单独创建一个日志处理器，把请求标识绑在对象上，而不是放在 ThreadLocal 里——因为 Agent 内部执行可能会切线程。

也如实说一下边界：这套设计目前是 **单进程内存态** 的，会话、运行期 Agent 配置、流式上下文都在 JVM 里，所以还不支持多实例和重启恢复；数据库和 Redis 只有环境脚手架，业务上还没接进去。这是我清楚的下一步。

### 精简版（30 秒，面试官只想要一句话时用）

> 这是一个 AI 驱动的数据搜集和绘图工作台。用户说一句话，后端拉起一个 Agent 工作流，按"分析、绘图、审查"三步跑，产出一张能在页面直接看的架构图。我做的主要不是业务，而是把这个大模型应用做成一个可控的服务：**第一，让模型只输出结构化 JSON、后端确定性地生成绘图 XML，解决模型直出 XML 不稳定的问题；第二，Agent 要执行本机命令，所以加了命令策略审查和用户交互审批，再加上按请求隔离的 shell 执行；第三，流式推送执行过程时的日志要按请求隔离，避免并发串线。** 目前是单进程内存态，还不支持多实例。

### 回答背后的核心逻辑

1. **先形态、再细节**：面试官第一句只想知道"什么系统、什么规模、为什么这么切",所以"为什么是单体不是微服务"要主动交代，这是加分项而不是可省略项。
2. **主动降维框架**：ADK / Netty 这类名词只说"它在系统里扮演什么通用角色"。否则面试官的注意力会停在"我没听过这个框架"，而不是停在你的设计上。
3. **用"问题 → 取舍"代替"功能清单"**：三块重点每块都先给一个真实问题（XML 不稳、命令危险、日志串线），再说选择和理由。功能清单没有技术含量，问题才有。
4. **主动暴露边界**：内存态、无持久化是明显短板。与其被追问打脸，不如自己先框定范围，反而显示你对系统有掌控。
5. **留追问钩子**：JSON 中间表示、审批二次校验、对象级上下文这三个点，都是面试官很容易接话往下问的，答案都已在 `docs/interview/` 其余几篇里备好。

### 面试官可能继续追问

1. "让模型只输出 JSON、后端翻译成 XML，那模型输出的 JSON 就一定合法吗？"（大概率第一个追问）
2. "策略审查的三态是怎么合并的？一条命令里拼了好几条子命令呢？"
3. "审批要等用户点，这个等待会不会把线程占死？"
4. "为什么日志上下文不用 ThreadLocal / MDC？那请求标识怎么传下去？"（→ D1）
5. "会话为什么放内存 Map？多实例怎么办？"
6. "流式推送怎么实现的？SSE 还是 WebSocket？"（→ D6）
7. "Agent 之间的中间结果怎么传递的？"
8. "这个方案上线了吗？并发多大？"（**不要编数据**，见下）

### 如果面试官继续深入

**追问 1（JSON 合法性）的下一层：**

> 模型输出的 JSON 我**不假设它一定合法**，所以中间表示这层做的是"解析 + 校验 + 兜底"三件事。
>
> 解析上，模型经常会在 JSON 外面包一段解释文字或者 Markdown 代码块，所以我不会拿整段文本直接反序列化，而是从输出里**扫描出候选 JSON 片段**再尝试解析。
>
> 校验上，我按结构逐项过：引用了不存在节点的连线直接丢掉，重复的节点 ID 只保留第一个，出现我不认识的语义类型就回退到默认样式。也就是**坏数据降级，而不是让整张图失败**。
>
> 兜底上，如果这一层完全解析不出来，就退回旧路径——继续按文本里有没有完整 XML 来判断，前端也保留了对 XML 的兼容。所以这一层是"尽力而为 + 可回退"，不是硬失败。
>
> 但这里有个我保留的欠账：**旧路径的 XML 我不做完整合法性校验**，只看有没有根节点标签。所以模型如果绕过中间表示直接吐了一段残缺 XML，用户是有可能看到渲染不出来的图的。这个是已知的。

**追问 8（上线规模）的下一层——必须诚实：**

> 这个项目我如实说，目前是**单进程内存态、没有真实的多实例部署和压测数据**，所以并发量我不会给数字。我能明确讲的是**设计上的并发边界**：会话、运行期配置、流式上下文都只在单个 JVM 内，重启即丢，多实例不共享；本地命令的执行是全局串行（有界单线程执行器 + 超时兜底），并发 shell 数有上限、达上限淘汰最久未用的空闲 shell；待审批命令有全局 5、单请求 1 的两级上限，超限直接拒绝而不是排队等线程。这些都是我一个一个定出来的数，但它们是**保护性上限，不是压测出来的容量**。

## 附：不同岗位侧重下的一句话版本

- **偏架构 / 中间件岗**："核心是把 Agent 的执行做成配置驱动的串行工作流，难点在请求级隔离——日志上下文绑对象不绑线程，本地命令执行按请求隔离 shell 并串行化加超时。"
- **偏业务 / 后端开发岗**："核心是把大模型的非确定性输出收敛成确定性的交付物：模型只出结构化 JSON，后端负责校验降级和最终 XML 的生成。"
- **偏安全 / 平台岗**："核心是给 Agent 的命令执行能力加边界：默认拒绝的策略审查、一次性交互审批、审批后二次校验、执行隔离与并发上限。"
