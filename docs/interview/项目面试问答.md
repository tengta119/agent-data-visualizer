# 项目介绍



这个项目是一个基于 Spring Boot 和 React 的 Agent 装配框架。用户通过配置文件定义 Agent 使用的模型、工具和处理流程，由框架完成校验、装配和执行。我基于这个框架搭建了一个 AI 绘图工作台，用户用自然语言描述需求，系统就能生成可以在 Draw.io 中展示的图形，减少手动画节点和连线的工作。

这个框架主要有两个特点。

第一个是**工作流可以组合和嵌套**。它支持串行、并行和循环执行，每个节点既可以是一个 Agent，也可以是一个子工作流。比如绘图任务可以先由需求分析 Agent 整理需求，再进入并行工作流，让两个绘图 Agent 同时生成方案，最后交给审阅 Agent 检查结果。这样用户可以根据任务配置处理流程，也能把已有流程作为子工作流复用。

第二个是**执行过程可观察、可控制**。用户能实时看到模型和工具的执行日志；如果 Agent 需要获取本机或远程环境信息，可以调用命令工具。命令执行前会经过策略检查，当前开发配置下还需要用户一次性审批。用户也可以在运行期间更新模型、工具和工作流配置，后端校验成功后切换到新配置，不需要重启服务。

目前这个框架已经用于 AI 绘图场景，会话和运行期配置主要保存在内存里，持久化和正式的后端认证还没有实现

## Q3

第一问：requestId 从哪里产生，又如何贯穿一次 Agent 执行，最终把事件推送到正确的前端连接？

请按你实际代码说明这条链路：

TEXT
前端发起请求
    ↓
创建 requestId / 注册事件回调
    ↓
执行 Agent，进入串行或并行节点
    ↓
模型、工具、子 Agent 产生事件
    ↓
根据 requestId 推送到对应前端连接
    ↓
执行结束，清理回调和连接关联
重点讲清楚三个实现细节：

回调保存在哪里？是每次执行显式传入一个回调对象，还是通过共享的 Map<requestId, callback> 查找？前端推送使用 SSE、WebSocket，还是其他方式？
并行任务如何保留请求归属？requestId 是显式放进执行上下文，还是依赖 ThreadLocal？子 Agent 和异步工具调用如何拿到它？
生命周期如何结束？正常完成、执行异常、用户断开连接时，分别如何清理？清理后如果还有子任务产生事件，代码会怎么处理？

## A3

## 面试回答

我这里把**日志归属**和**前端连接**分开处理。前端发起 `POST /api/v1/chat_stream` 后，后端为这一次调用生成 UUID 作为 `requestId`，创建一个 HTTP 流式响应对象，并在共享的连接表里登记 `requestId → 前端连接`。随后异步执行 Agent，同时**给这次执行传入一个独立的事件回调**。回调捕获本次请求的 `requestId`；它不是从共享的 `Map<requestId, callback>` 里查出来的。共享 Map 保存的是前端连接，不是回调。

Agent 执行到模型、工具或子 Agent 时，产生的执行事件会沿这次执行的回调往上送。串行节点直接传递回调；并行节点启动各分支时，也把**同一个请求回调显式传给分支**。所以分支换了线程，日志仍然归属于原请求，不靠 ThreadLocal 猜测“当前是谁”。回调拿到事件后，用捕获的 `requestId` 查询连接表，向对应浏览器写入连续的 JSON 消息。这里用的是 **`ResponseBodyEmitter` 的流式 HTTP 响应**，不是 WebSocket，也不是浏览器 `EventSource` 所用的标准 SSE 格式。

正常完成时，后端发送最终 `result`、`done`，然后结束连接；执行异常时尽量发送 `error` 并结束连接。完成、超时、连接报错，以及执行任务的 `finally`，都会走同一套**只执行一次**的清理逻辑：取消当前请求的执行任务，移除连接映射。用户断开连接通常通过连接回调或后续写入失败触发清理，不能说浏览器一断开，所有外部调用就一定立刻停止。清理后即使还有晚到事件，路由时也查不到这个 `requestId` 的连接，事件会被丢弃，不会发到别人的连接。

## 这个回答背后的核心逻辑

```text
请求级回调捕获 requestId
    → 串行/并行分支显式传递回调
    → 共享连接表按 requestId 找到 ResponseBodyEmitter
    → 清理时删除映射，晚到事件无处投递
```

要区分两条上下文链：**日志事件靠显式传递的回调归属请求**；Shell 等工具需要执行审批时，请求上下文另行显式传入工作流，再由工具调用层带到并行工具线程，并只在工具适配器入口短暂绑定线程上下文。不能把工具的 ThreadLocal 说成日志路由机制。

## 面试官可能继续追问

- 多个并行分支同时写一个前端连接，会不会把 JSON 写乱？
- 为什么不用 `sessionId` 路由日志？
- 连接已经移除，但模型调用还没真正结束，怎么办？

## 如果面试官继续深入

每次工作流执行有自己的事件锁，分支调用回调时会串行进入；连接对象本身也有发送锁，避免并发写入交错。`sessionId` 可以承载多轮对话，但 **`requestId` 唯一对应这一次流式 HTTP 调用**，因此用它路由。取消会传给正在执行的 Agent，并中断异步任务；这是尽力取消，已经发往外部进程或远程主机的操作不保证撤销。当前默认工作流入口是串行的，并行节点是代码支持、配置中存在但**不是默认入口**的路径。

TEXT

主执行任务：发送 result、done，结束连接

请结合代码回答：

并发写入：各分支是否直接调用 ResponseBodyEmitter.send()，还是先进入请求级队列，由单一发送者写入？前端靠什么识别连续 JSON 的消息边界——换行分隔、长度字段，还是其他协议？不要仅以“调用了一次 send()”推断浏览器就会收到一个完整消息块。

## A4

## 面试回答

我这里**没有请求级日志队列或单独的发送线程**。并行分支产生事件后，调用这次执行共享的回调；回调进入本次执行的事件锁，再按 `requestId` 找到前端连接。连接对象还有一把发送锁，各分支最终是在锁内调用 `ResponseBodyEmitter.send()`，避免同时写同一条响应。

前端也**不假设一次 `send()` 就对应一次 `reader.read()`**。后端发送的是连续 JSON 对象，没有用换行或长度字段做消息边界。前端把收到的字节块持续解码、放进缓冲区，扫描 JSON 的花括号深度，同时处理字符串内的括号和转义字符；找到完整对象后才解析。

`done` 不会在**正常执行**时抢在并行分支前面，是因为主执行任务必须先等工作流返回。并行节点会等待各分支的 `CompletableFuture` 完成，再合并结果；只有整个工作流返回后，控制器才发送 `result` 和 `done`。如果某个分支失败，并行节点会请求取消正在运行的 Agent，**继续等待其他分支结束**，然后向上抛错；控制器走 `error` 路径，而不是把失败当成功发送 `done`。等待期间，其他分支仍可能产生事件；连接尚有效时，这些事件仍可能被推送。这不是“失败瞬间停止所有日志”。

清理竞态也确实不能只用“Map 查不到就丢弃”解释。代码从 Map 取出连接后，会在发送锁内**再次检查**连接的 `completed` 标记；如果清理已经把它置为完成，就不发送。但还有更窄的窗口：发送线程通过第二次检查之后，另一个线程仍可能移除映射并标记完成，因为 `clear()` **没有获取同一把发送锁**。这时 `send()` 可能失败；当前代码会把连接标记为完成，并抛出运行时异常，由执行任务的异常和最终清理路径处理。**所以我不会声称当前实现能严格保证清理之后绝无一次发送尝试，也不会声称 `send()` 成功就代表浏览器已收到。**

## 这个回答背后的核心逻辑

- **正常完成顺序**靠“主任务等待全部并行分支返回 → 发送 `result` → 发送 `done`”，不是靠前端猜测日志何时结束。
- **并发写入**靠回调锁和连接发送锁，不是靠单消费者队列。
- **连接断开与清理**是尽力取消、丢弃晚到事件并处理写入异常，不是与网络发送严格原子化的交付保证。

## 面试官可能继续追问

- 如果一个分支始终不退出，等待全部分支会有什么风险？
- `clear()` 为什么不和 `send()` 共用同一把锁？
- 连续 JSON 的自定义分帧方式有哪些局限？

## 如果面试官继续深入

当前并行实现对成功分支逐个 `join()`；遇到失败会取消活动 Agent，再逐个 `join()` 排空其他分支，避免会话执行锁释放后仍有分支修改执行状态。但取消只能尽力而为；如果分支不响应取消，等待也可能拖长。发送方面，`sendLock` 保证同一连接内的写入不交错，却不构成“清理与发送”的完整互斥协议。前端的花括号扫描能处理任意 HTTP 分块下的连续 JSON，但它是项目自定义协议，不是标准 SSE。

## A5

## 面试回答

这里的“取消”主要是**取消 R1 自己正在执行的 Agent 和模型调用，并让工具在检查到取消状态时停止继续执行**；它不是把同一份 YAML 下的所有任务一起停掉。

同一份 YAML 在服务里会编译成共享的**配置定义**，但实际运行状态不放在这份定义上。每次创建会话都会得到独立的会话状态；阶段 Agent 按节点路径在**该会话内复用**。每个阶段 Agent 创建时又有自己的模型客户端和工具注册表；每次 Agent 执行还会创建自己的取消令牌。Shell 工具背后的服务、Netty 网关和工作流执行器是共享的，但远程命令用独立 ID 等待响应。

所以在你的例子里，R1 一个分支失败后，并行节点遍历的是 **R1 当前会话的活动 Agent 集合**，逐个调用 `cancel()`。这个调用会标记该 Agent 当前执行的取消令牌，并尝试取消它正在进行的 HTTP 模型请求。R2 即使使用相同 YAML，只要是另一个会话，它的 Agent、取消令牌和模型客户端都是另一套，不在 R1 的活动集合中。当前配置的模型客户端还有各自的 HTTP 请求调度器，因此 R1 的模型取消不会通过一个全局 `cancelAll()` 把 R2 的模型请求一起取消。

但**取消不等于撤销已经发出的远程命令**。如果 R1 另一个分支已经把命令发给远程客户端、正在等结果，Agent 的取消标记不会把远端正在执行的命令收回来。Java 网关对这条命令的响应等待是 **30 秒**；一直没有响应就超时并移除该命令的等待项。并行节点本身没有再设一个“所有分支最多等 N 秒”的总截止时间，它会继续 `join()` 等其他分支结束；流式连接的 20 分钟超时也不能被说成 `join()` 的严格等待上限。若换成不响应取消、又没有自身超时的工具，就不能保证并行节点及时退出。

## 这个回答背后的核心逻辑

```text
R1 分支失败
  → 取消 R1 会话中当前活动的 Agent
  → Agent 标记本次运行取消，并尝试取消其模型 HTTP 调用
  → 等 R1 其他分支结束后抛出失败
  → 控制器走 error / 清理路径

R2：另一会话的 Agent、取消令牌、模型客户端不在上述取消范围内
```

这里**不是**靠 `CompletableFuture.cancel(true)` 取消并行分支。并行节点失败时实际调用的是活动 Agent 的 `cancel()`，然后等待分支完成；请求整体清理时，控制器才会对它提交的异步执行任务调用 `Future.cancel(true)`。后者也不能保证已经发出的模型、工具或远程命令副作用被撤销。

## 面试官可能继续追问

- 同一个 `sessionId` 被两个请求同时使用，还能并行执行吗？
- 远程命令超时后，远端实际执行成功并迟到返回，会怎样？
- 如果工具没有超时、也不响应取消，如何给整个工作流加截止时间？

## 如果面试官继续深入

同一会话的 turn 有锁，不能像两个独立会话那样同时运行；上面 R1/R2 的隔离推演前提是**各自创建了会话**。远程命令的 30 秒是 Java 网关等待响应的上限，不是远端进程执行的撤销机制；超时后等待项已删除，迟到响应无法再完成原来的等待。当前实现依赖各外部调用自己的超时与协作式取消，**没有并行工作流级的统一硬超时**。

## A6

## 面试回答

**代码允许两个请求传入同一个 `sessionId`，但不允许它们在同一会话里重叠执行。** `/api/v1/chat_stream` 只有在请求没带 `sessionId` 时才新建会话；带了就复用。工作流运行时会先校验这个会话绑定的 Agent、用户和配置版本，再获取**会话锁**。所以如果 R1 正在执行，R2 会等锁，而不是立刻与 R1 同时进入同一个阶段 Agent。这里要说准确：代码有 `running` 状态检查，但主要隔离靠锁；通常 R2 是**排队串行执行**，不是收到“会话忙碌”错误。

阶段 Agent 是**按会话、按节点路径复用**的，因此它的对话历史也留在该 Agent 实例中，不是每个请求重新建一份。它持有模型客户端和工具注册表；模型客户端管理自己正在进行的 HTTP 调用。每次调用 `run()` 时，阶段 Agent 会创建新的取消令牌，设置本次执行的事件处理器，并在结束时解除当前令牌、关闭本次事件处理器。R2 要等 R1 释放会话锁后才能进入这个 Agent，事件回调也由 R2 这次调用单独传入，不会从 Agent 的历史里读取 R1 的 `requestId`。

R1 的迟到清理尤其需要防护：取消入口不仅找 `sessionId`，还会比较会话里记录的**当前活动 `requestId`**。如果 R1 已经结束、R2 已经接手同一会话，R1 的取消请求因 ID 不匹配，不会取消 R2。R1 的日志回调始终捕获 R1 的 `requestId`；即使有晚到事件，也只会尝试找 R1 的连接，不会被改派给 R2。

## 相关对象和核心伪代码

```text
SessionState:
  lock                         // 同一会话的 turn 串行
  stageAgents: 节点路径 → Agent // 在该会话内复用，持有对话历史
  activeAgents                 // 当前正在运行的阶段 Agent
  activeRequestId              // 当前 turn 的请求 ID

EmbeddedAgent:
  agent                        // 持有该阶段 Agent 的对话历史
  llmClient, tools             // 随阶段 Agent 创建
  currentRun: CancellationToken
  pendingCancel
  // 本次事件处理器在 run 时设置给内部 agent，结束时关闭

execute(request, listener):
  session.lock.lock()
  try:
    校验会话归属和配置版本
    session.activeRequestId = request.requestId
    从 session.stageAgents 获取或创建阶段 Agent
    session.activeAgents.add(stageAgent)
    try:
      stageAgent.run(input, 本次事件回调 listener)
    finally:
      session.activeAgents.remove(stageAgent)
      session.activeRequestId = null
  finally:
    session.lock.unlock()

stageAgent.run(input, listener):  // Agent 实际还会对 run 串行化
  token = new CancellationToken()
  currentRun = token
  设置本次事件处理器(listener)
  try:
    执行模型和工具调用
  finally:
    清除 currentRun，关闭本次事件处理器

cancelRequest(request):
  session = 按 request.sessionId 查找
  if 请求的 agentId、userId 匹配
     且 request.requestId == session.activeRequestId:
    对 session.activeAgents 中的 Agent 调用 cancel()

stageAgent.cancel():
  如果 currentRun 存在：
    token.cancel()
    llmClient.cancelInFlightCalls()
  否则：
    标记 pendingCancel，供紧接着开始的 run 检查
```

这题里我不能只说“断开后会取消”。**R2 等待会话锁时，取消工作流和取消后台任务是两条不同的路径。**

会话用的是 `ReentrantLock`，获取时调用 **`lock()`**，不是 `lockInterruptibly()`，也没有等待超时。因此 R2 即使被中断，也**不会立即退出锁等待**，它仍可能等到 R1 释放锁、自己拿到锁。

R2 断开并触发清理后，服务端会按 R2 的 `requestId` 尝试取消当前活动的 Agent。但这时会话的活动请求还是 R1，ID 不匹配，所以**不会误取消 R1，也取消不到尚未成为活动请求的 R2**。真正针对排队中 R2 的，是控制器保存的那次请求的 `Future`：清理时会调用 `cancel(true)`，向 R2 的后台执行线程发出中断。如果 R2 还没开始运行，任务可以不再启动；如果已经卡在 `lock()`，中断不会让它马上离开锁等待。

不过，代码在 **R2 拿到锁、进入工作流之前检查了线程中断状态**。所以在“R2 等锁期间，它的后台任务已被 `cancel(true)` 中断”这条路径上，R2 拿到锁后会因中断抛错，不会继续调用模型或工具。这里不能误说成 `lock()` 响应了中断；真正挡住执行的是**拿锁后的中断检查**。

## 获取锁到释放锁的简化伪代码

```text
session.lock.lock()                  // 不可中断等待，无等待超时
try:
    校验配置版本、找到 Agent 定义
    session.running = true
    session.activeRequestId = R2.requestId
    try:
        if 当前线程已被中断:
            抛出“请求已取消”
        执行工作流                    // 到这里才可能调用模型、工具
    finally:
        session.running = false
        session.activeRequestId = null
finally:
    session.lock.unlock()
```

控制器在提交任务后保存 `Future`；清理时会调用请求级取消，并对尚未完成的 `Future` 调用 `cancel(true)`。如果清理恰好发生在 `Future` 保存之前，控制器保存它之后还会检查清理标记，再调用 `cancel(true)`。

## 这个回答背后的核心逻辑

**在题目给定的时序下**，R2 已经排队，随后断开且清理成功触发中断：它可能继续占着一个后台线程等锁，但拿锁后会检查中断，**不会因为“锁终于空了”就正常开始 Agent 执行**。

边界也必须说清楚：拿锁后代码检查的是**线程中断标记**，不是再次检查前端连接是否存在；检查与真正开始执行之间也不是原子操作。如果清理发生得更晚，例如 R2 已通过检查、已经发起模型调用或远程命令，就只能尽力取消，**不能保证没有模型费用或远程副作用**。另外，用户关闭页面是否被后端立即发现，取决于连接回调或后续写入失败；不能把“用户关页面”直接等同于“服务端已经完成清理”。

```java
            if (session.version != current.get().version) session.closeAgents();

    } finally {
        session.lock.unlock();

}
```

## 面试回答

在你给的时序里，**R1 的绘图阶段仍使用 V1**。R1 在拿到会话锁、开始这轮执行时，已经从当前快照取出了 V1 的工作流定义；后面的分析、绘图等节点递归执行时，传的是**同一个定义对象**，不会每到一个节点就重新读全局配置。所以 V2 发布不会让 R1 出现“分析用 V1、绘图用 V2”的混用。

更新时是先复制配置、编译和校验，成功后用 `AtomicReference.set()` **一次替换当前快照**。旧快照仍可供已进入的 R1 使用；更新失败则不会执行这次替换。这里的“原子”指**快照引用切换**，不是说能原子地替换所有在途 Agent。

**R2 带着 R1 的旧 `sessionId` 不会自动升级到 V2。** 这个会话创建时绑定了 V1 版本。R2 如果在 R1 执行中到达，会先等同一把会话锁；拿到锁后读取当前 V2，发现会话版本不匹配，就报“会话已过期”，需要创建新会话。R1 结束时，如果发现当前版本已变化，会关闭并清空旧会话缓存的阶段 Agent；更新发布时，空闲旧会话的阶段 Agent 也会被尝试关闭。**旧会话的映射并没有因此迁移到 V2。**

## 这个回答背后的核心逻辑

**请求内一致性**靠“开始执行时取一次定义并向下传递”；**请求间版本边界**靠“会话版本与当前快照比较”。两者结合，既不打断 R1，也不让 R2悄悄拿旧历史运行新配置。

## 面试回答

你给出的竞态——更新线程只看见 `running == false`，随后请求启动，它却直接关闭正在使用的 Agent——**按当前代码不会这样发生**。原因是更新线程关闭旧 Agent 前，也要尝试获取**会话执行用的同一把锁**，不是单凭 `running` 字段判断空闲。

```java
// V2 已完成编译并发布
current.set(v2Snapshot);

for (SessionState session : sessions.values()) {
    if (session.version != v2Snapshot.version
            && session.lock.tryLock()) {
        try {
            if (!session.running) {
                session.closeAgents();
            }
        } finally {
            session.lock.unlock();
        }
    }
}
// tryLock 失败就跳过，不等待正在执行的请求
```

如果更新线程先拿到锁，请求线程就不能同时启动，旧 Agent 会先被关闭；随后请求拿锁时发现会话版本是 V1、当前配置是 V2，直接拒绝。如果请求线程先拿到锁，更新线程 `tryLock()` 失败并跳过，不会碰它正在使用的 Agent。**R1 正常进入 V1 执行后**，会在执行结束的 `finally` 中检查版本，并在**释放会话锁之前**关闭、清空旧阶段 Agent。

## 这个回答背后的核心逻辑

保护 Agent 生命周期的是**同一把会话锁**：请求执行和旧 Agent 清理不能同时持有它。`running` 是拿锁后的辅助判断，不是独立的并发保护机制。`tryLock()` 失败采取的是跳过，避免热更新线程被长时间运行的请求阻塞。

## 面试官可能继续追问

- 更新线程跳过清理后，如果请求拿锁却因版本过期而拒绝，谁清理旧 Agent？
- 旧 Agent 关闭时抛异常，快照发布会回滚吗？
- 快照能否称为深度不可变？

## 如果面试官继续深入

这里有两个不能美化的边界。

**第一，旧 Agent 清理存在遗漏窗口。** 更新线程发布 V2 后 `tryLock()` 失败；而持锁请求如果尚未真正进入执行，在读取快照时发现 V2，可能直接抛出会话过期异常。这个异常发生在“运行结束时关闭旧 Agent”的那段 `finally` **之前**，于是这次不会清空旧 Agent。它可能留在旧会话缓存中，直到后续更新尝试清理或应用关闭。所以当前做到了“不并发关闭正在使用的 Agent”，但**不能保证每次更新后立即清理全部旧 Agent**。

**第二，快照也不能称为递归不可变。** 安装前会对输入配置做 JSON 序列化/反序列化复制；编译后的外层定义 Map、阶段 Map、工作流 Map 和子节点 List 使用不可修改副本，模型配置与指令主要是字符串或 record。但阶段定义里的**工具配置列表只复制了容器，元素仍是可变配置对象**。现有执行路径没有把原始调用方的配置对象直接留在快照里，不过代码没有彻底冻结所有嵌套元素。

最后，释放锁位于 `finally`：即使关闭过程中抛异常，锁仍会释放，不会因此一直锁住该会话。但快照引用是在清理之前就发布的，**清理失败不会自动回滚 V2**；异常还可能导致本次旧 Agent 缓存没有完全清空。

# Q18 

并行执行的原理是什么，一个工作流只支持并行或者串行，还是说一个工作流里面可以有串行和并行

# A18

## 面试回答

我这里的并行执行，本质上是**把多个子任务提交到线程池，让它们可以同时执行，然后等待结果汇合**。比如两个绘图 Agent 可以分别调用模型生成方案，不需要等第一个生成完，第二个才开始。实际能同时运行多少个任务，还取决于线程池的容量。

每个分支都有独立的 Agent 实例，以及一份执行前的状态副本。这样两个分支不会直接修改同一份结果状态。等所有分支成功结束后，主流程再按配置顺序合并它们的结果；如果某个分支失败，就尝试取消其他活跃 Agent，等待分支收尾后再抛出异常。

至于串行和并行，**一个工作流节点只有一种执行类型，但整个工作流可以通过嵌套组合串行和并行**。因为它的子节点既可以是 Agent，也可以是另一个工作流。

比如外层是串行：先分析需求，再执行一个并行绘图工作流，里面两个绘图 Agent 同时生成方案，等它们都结束后，再执行审核。反过来，外层并行、每个分支内部串行，也支持。

## 这个回答背后的核心逻辑

区分两个层次：

- **单个节点**：选择串行、并行或循环中的一种。
- **整个流程**：子工作流递归嵌套，可以组合多种执行方式。

例如你前面给出的配置：

```
串行工作流
    分析 Agent
        ↓
    并行工作流
        ├─ 绘图 Agent A
        └─ 绘图 Agent B
        ↓ 等待两个分支结束
    审核 Agent
```
