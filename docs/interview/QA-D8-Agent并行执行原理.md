## D8. Agent 是如何并行执行的？底层原理是什么？是多线程吗？

**Q：你说工作流支持并行节点，多个 Agent 并行执行。这个并行底层是怎么实现的？用的多线程吗？线程池配的多大？**

### A：面试回答

我们项目里多个 Agent 之间的并行，本质上不是靠线程池做的，而是靠**响应式事件流**做的。

先说背景：我们的绘图流程是"分析 → 绘图 → 审查"的工作流。为了支持同一个需求出多版候选图形方案，我把工作流组织成一棵树：串行节点保证前后依赖，并行节点下面挂多个子 Agent，最后由审查 Agent 挑或者融合候选。

实现上，并行节点底层用的是 RxJava 的 merge 操作——每个子 Agent 执行后返回一条事件流，merge 把这些流**同时订阅、合并成一条流**，谁先产出事件谁先往下游发，不会等前一个跑完才启动下一个。串行节点对应的是 concatMap，前一条流完整结束才开始订阅下一条，所以两种节点可以嵌套出"前置分析 → 并行出候选 → 后置汇总"的结构。

这里有一个我踩过坑之后才想明白的点：**merge 的"并行"只是订阅语义上的并行，它本身不创建线程**。整棵 Agent 树在构建时全是惰性操作符——只是把"该做什么"组装成一张蓝图，一行执行业务代码都没跑；直到某个线程订阅根流，回调才沿操作符链在这个线程上依次拉起所有子流。编排层没有线程池、没有调度器切换。所以真正能不能并发，取决于子 Agent 最底层那个模型调用是什么形态——

如果底层是同步阻塞的 HTTP 调用，第一个子 Agent 会一直阻塞到模型返回，第二个才开始；看起来是并行结构，实际耗时还是串行之和。如果底层是流式的异步 HTTP，请求发出去就立刻返回，响应数据由 HTTP 客户端自己的 IO 线程回调投递，那多个模型的**等待时间才是真正重叠的**。我们项目两条路径都有，我在排查并行分支"没有提速"的问题时把底层调用扒开看过，确认了非流式配置下并行确实退化成了同线程串行。

所以这个方案里，并发的真实性能不是 Agent 编排层给的，是由底层网络客户端的异步 IO 兑现的。多个请求共享一小池 IO 线程，靠多路复用而不是"一个 Agent 一个线程"来重叠等待。这在模型调用这种纯 IO 等待场景反而是好事——不用为每个 Agent 占一个业务线程，业务线程数不随分支数膨胀。

然后是并行 Agent 之间怎么传数据。它们不共享返回值，也没有方法参数互传，靠的是一份**共享的会话状态**。每个 Agent 配置一个输出键，执行完把自己的结果写进这个状态；后续 Agent 的提示词里用占位符引用这些键。串行下这是天然的管道——前一个写、后一个读；并行分支之间互不等待，所以原则是每条分支必须用**独立的输出键**，候选 A、候选 B 各写各的，最后审查 Agent 把两个键都读出来汇总。

边界问题我也主动说一下。第一，并行分支如果写了同一个状态键，就是并发覆盖，最后留哪个取决于谁先完成，而完成顺序由模型和网络响应时间决定，不确定的——我们早期配置就犯过这个错，两个并行分支复用了同一个输出键，审查 Agent 永远只能看到一个候选。第二，merge 不做结果汇总，多条分支的输出是交错到达的，下游要么按事件里的来源标识区分展示，要么专门设一个汇聚 Agent。第三，这条并行链跑在发起请求的工作线程上，我们流式接口用的是 CompletableFuture 默认公共池；如果要把每个子 Agent 调度到独立线程池，得在流上显式加调度器，这块目前没有做。

### 回答背后的核心逻辑

这题的陷阱在最后那句"线程池配的多大"——顺着答"配了 X 核 Y 线程"就露馅了，因为编排层根本没有线程池。正确姿势是**先破题（"不是线程池"），再给机制（惰性事件流 + merge 订阅语义），最后主动交代"并行的真实性由底层 IO 形态决定"这个源码级结论**。中间穿插"排查并行没提速时扒开底层看过"，把结论包装成实测经验而不是背书。三条边界（覆盖、交错、公共池）都是真实存在的项目事实，主动缴械面试官的追问弹药。

### 面试官可能继续追问

1. "响应式流和线程池 + CompletableFuture 比，优劣在哪？"
2. "多个线程往同一条流里发事件，线程安全怎么保证？"
3. "并行分支写同一个状态键的覆盖问题，你们怎么修的？加锁了吗？"
4. "共享会话状态是内存的吗？服务重启或多实例怎么办？"
5. "那你们并行到底有没有真的变快？怎么验证的？"

### 如果面试官继续深入

**追问 1（vs 线程池）**：CompletableFuture 是"一个结果"的抽象，粒度是任务；事件流是"一批陆续到达的数据"的抽象，粒度是事件。Agent 执行天然边生成边产出事件（模型 token、工具调用、中间结果），Future 表达不了中间态。线程池方案要为每个分支占一个工作线程直到结束；事件流方案里等待发生在 HTTP 客户端的 IO 线程上，业务线程数不随分支数膨胀。代价是回调链路深了之后调试栈不直观、可观测性差，我们就是靠给每个请求挂独立的事件监听才把执行日志看清的。

**追问 2（线程安全）**：RxJava 规范要求同一个订阅的 onNext 必须串行调用。单条子流内部的异步投递由它自己的订阅链保证串行；merge 层对多条子流做了序列化，不会有两个线程同时向同一个下游推事件。所以并行的效果是"事件按到达时间交错、但每条分支内部有序"——这也是为什么我们的流式日志里多个 Agent 的输出会穿插出现，要按事件携带的来源标识分组才能还原每条分支的完整输出。

**追问 3（覆盖修法）**：没用锁。根因不是并发写冲突，而是"两个逻辑上不同的产出共用了同一个名字"。修法是配置层面拆分：每条分支独立名称、差异化指令、独立输出键，汇聚方显式引用全部键。写覆盖只发生在同 key 上，拆开 key 之后各分支互不可见、天然无冲突。这题如果回答"加 synchronized"就跑偏了——数据竞争是表象，命名冲突才是本质。

**追问 4（状态共享）**：目前是纯进程内存，会话和状态都不落库，重启即失、不支持多实例。这是明确的单实例工作台定位，不是疏漏。如果要水平扩展，要把会话状态迁到外部分享存储并定义会话归属；MySQL/Redis 环境有编排但业务代码没接入，我不会把它说成已实现。

**追问 5（有没有变快）**：诚实答案是"取决于配置"。走流式异步模型调用时，并行组墙钟时间约等于最慢分支，多个候选方案生成的网络等待真正重叠；走非流式同步调用时没有收益，就是同线程排队。我们的验证方式很朴素：在分支前后打带时间戳的执行日志，对比串行和并行的总耗时曲线——串行是各分支之和，流式并行收敛到最慢分支。这个测法也暴露了一个改进点：编排层缺分支级超时，一个分支卡死会挂到上层流式接口的 20 分钟总超时才释放（对应 D5 里讲过的 fail-fast 缺口）。
